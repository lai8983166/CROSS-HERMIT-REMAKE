## Context

见 proposal.md。Godot 原型已产生一次性终局快照，并把来自 `T0005.BIN` 的 112 请求与本地胜负分离；尚没有持久角色档、战斗脚本执行器或学园周历控制器。原版不是单一「胜利回调」：`4CE8F0` 分发 opcode 112 到 `42D960 → 4978C0` 的战术工作区；`451670 → 451A60 → 4539B0 → 454CF0` 包含战术任务的 VM 更新。同时 `4519C0 → 452FC0 → 499C90` 初始化并行的 UnitCtrl 结束判定，`4539B0 → 46B470 → 499DA0` 按帧处理；其相位 6 传给 `4549D0` 的任务结束标志为 0，不能代替 `454BB0` 等条件调用者传入的 1。`49E2B0` 状态表的 11 → `4BD6F0/4BD660` 战术结果、10 → `4B9120/4B8FF0` 准备/场次循环、12 → `4C1D30/4C1AA0` 总战果。`4B8FF0` 在 `DAT_007A5296==DAT_007A5298` 时请求 12，否则处理下一场并请求状态 16。`4C1AA0` 中条件分支 0、2 调用 `4C1350`，仅分支 2 调用 `4D3510`；原始分支号不是胜负标签。`4D3510` 还处理参与者、解锁与道具整理。场景 5 哪个事件会设置战术结束标志、以及它与 112 的先后关系仍未闭合。

## Goals / Non-Goals

**Goals:**
- 让每次状态变化能回溯到脚本指令、战果任务的分支及原版函数地址。
- 让战斗终局只提供事实快照，由独立转接层决定是否具备持久事务依据。
- 完成至少一条由真实脚本出口到角色/日历结果的可重放纵向样例。

**Non-Goals:**
- 不实现完整 YBC32 VM、剧情 UI、全量掉落或存档格式。
- 不把 `Battle.winner`、opcode 名称或战果画面外观当作足够的分支证据。
- 不改既有战斗直接运行入口，也不把所有战斗都强制绑定学园流程。

## Decisions

1. **证据先行且分支默认封闭。** 第一批任务追踪 opcode 112、147/148、战术返回缓冲、战果任务构造/退出、`4C1350`/`4D3510` 的实际调用边与脚本语料。原始数值、函数地址和业务解释分别列栏；未闭合的解释标为 unresolved。对照方案是直接从反编译函数名/旧文档猜含义，风险是把 `PUTTACTRET` 或战利品初始化误认为最终持久写入。
2. **终局事实与脚本结果双轨。** `Battle` 首次结束时深拷贝一个终局快照，包含帧、胜方和本场单位身份/终态；既有 `finished/winner` 保持兼容。脚本结束请求作为另一事件输入，带脚本文件、块/子程序、指令偏移、原始参数和来源 tick。跨系统转接层要求两路信息和已证明的战果分支契约，而不是看到任一路就自动推进。这样原型仍可独立跑战斗，也能容纳脚本驱动结局。
3. **持久角色 ID 不从数组位置或名字推断。** 战斗内数组索引只用于回放；持久档映射使用显式原版角色 ID。样例缺少对应 ID 或证据时报告 unresolved 并保持持久档不变。对照方案是按序号或显示名写回，阵容/同名/敌方模板改变时会写错档。
4. **战果事务按源分支分离。** 定义结果处理记录：`battle_instance`、原始脚本请求、原始分支键、已证明的角色字段变更、战果展示请求与周推进请求；各项都有独立证据引用。确认分支后按原版顺序应用，日志记录 before/after，完成后按实例键去重。未知分支不作部分猜测性提交。对照方案是将所有变化并入 `winner` 回调，无法解释非普通战斗或同结果重送。
5. **周推进不是裸计数器。** `4D3510` 的月周进位与参与者更新、整理调用须分别审计。如果这些副作用的必要顺序/范围尚不明，转接层可以记录待处理请求，但不得报告「周推进已完成」或仅把 week 加一。月周输出与角色写回的共同事务必须能从固定输入确定性重放；如果证据使当前规格无法满足，就先更新提案/规格，不能静默缩小任务。
6. **离线来源与确定性。** 用现有 T*.BIN 反汇编和最小来源描述提供一条实证脚本样例；不在运行时解析原版二进制。Godot 逻辑测试覆盖普通/特殊/未知分支、月末进位、重复送达和中断。Python 检查源数据及导出，无随机调用游离于注入种子。
7. **显式任务状态与场次门槛。** 战术脚本指令、本场结束、状态 11 的战术结果、状态 10 的准备任务、状态 12 的总战果是不同事件。结果输入新增原始任务状态和 `DAT_007A5296/5298` 场次进度；状态 10 未完成或进入状态 16 时，不得生成状态 12 的角色/周历事务。先追踪一条脚本实例从 112 到战术任务退出的实际控制边，再实现最小可回放状态转接；若该边仍缺失，只记录待定，不用 `winner` 补足。此决策不要求重制准备界面，但要求保留它对总战果的时序门槛。
8. **场景事件与 112 分开核对。** 场景 5 的脚本 112 进入 VM 等待，不等于 `TacticsTask+0x4C=1`。先沿 `454BB0/4549D0` 的真实实参、调用者以及 `4519C0/452FC0/499C90/46B470/499DA0` 的并行链追出实际触发条件，核对场景 5 的事件配置和先后顺序；必要时以只读运行时轨迹补足静态缺口。只有同一可核对场次把事件、任务结束标志及状态 11 连上，才提升该脚本样例的适用性。若仍不闭合，保留来源事实和缺失边，不能把两条并行调用链凭函数名拼接。

## Risks / Trade-offs

- [反编译器对函数形参/局部变量的误判] → 关键分支和数据写入用汇编、调用方及脚本实例交叉核对；不凭单个伪 C 签名结论实现。
- [脚本退出与本地全灭条件不一致] → 两路事件独立记录；不合并时保持待定并给出诊断。
- [周结算牵涉超出本次可验证范围的副作用] → 停止自动日历写入，更新变更规划并向用户说明新增范围，不把未完成事务标成已完成。
- [非持久单位混入参战数组] → 显式角色 ID 缺失时不回写；战斗回放仍允许。
- [旧文档把初始化计算称作战后发奖] → 在审计中注明调用时机，保留经证实的规则、纠正错误时序。
- [准备任务可能遍历多场或进入状态 16] → 按场次计数记录每次状态迁移；未到状态 12 不提交角色/周历，避免把第一场战果误当作最终结果。
- [场景 5 的 112 与独立结束判定没有已知因果边] → 分别核对 `+0x92E0` 等待、`+0x4C` 结束标志及其调用者；静态不可判定时记录缺口并寻求只读运行时证据，不以任一信号代替另一信号。

## Migration Plan

先分次提交原版调用链及脚本实例证据，再闭合状态 11→10→12 的场次门槛；战斗终局快照与脚本请求已独立落地，随后分别提交受证据约束的转接/持久档、周历事务和回归测试。保持旧 `finished/winner` 与样例配置可用。出现证据缺口则暂停对应写入，不用虚构数据通过测试；需要回退时按独立提交恢复，不覆盖其他项目变更。
