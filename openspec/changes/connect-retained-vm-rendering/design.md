# Design

## Context

原检查点由有来源的场景/任务/VM执行形成，原游戏根地址1000000h，三个案例有相同的未初始化渲染前提。旧初始化工具已完整执行412E30及413450，但使用独立owner地址且助手已经结束。R1另提供真实新启动的空缓存初值和完整对象关系。

## Goals / Non-Goals

Goals: 在有效资源寿命内重建渲染上下文、恢复保留场景的逻辑状态并执行原矩形/文字到真实设备输出。区分检查点重建和不改变任何状态的原地继续。
Non-Goals: 不模拟原保护层、不改Godot、不承担R3完整输入/世界帧，不用已结束进程地址作为可用句柄。

## Decisions

- 原初始化在声明的新CPU中执行，游戏根使用保留VM的1000000h地址；优先将现有工具的owner配置参数化，保持默认行为和旧证据。新启动输入在第一条原指令前声明，不在旧停点清零。
- 检查点恢复是明确的资源重建：从原初始化产生的渲染管理器、字体、设备及相关全局保留实际状态，恢复经校验的VM/任务/脚本和场景资源。逐区记录新旧来源和例外；不把此过程称为旧平台句柄恢复或未修改检查点的原地继续。
- 使用裁剪入口的已有祖先检查点保留原调用栈，避免在40E2D0手改已装载的ECX0。只有原40D970等写入初始化字段，原队列和绘制函数保持。
- 真实接口在同一拥有助手中服务；扩展通用有界绘制/读回协议，使用原代码生成的命令和顶点。所有原生接口输入输出和资源清理可核对，独立模型验证命令和像素。
- 以可观察功能为单元提交和验证，复用前缀/平台/校验工具；R2的完成需要保留VM矩形/文字路径与实际输出，独立设备成功不满足验收。

## Risks / Trade-offs

- 旧检查点本身没有有效GPU资源 → 用原代码建立新资源，明确每段恢复/保留来源，拒绝地址碰撞和失效句柄。
- 初始化会覆盖场景字段 → 明确逻辑/渲染状态分区并做完整内存及CPU/栈保留核对，未知交叠先调查来源。
- 平台绘制/读回差异 → 记录实际格式、接口结果及容差依据，空白输出不能算成功。
- 临时参数化污染旧工具 → 限定新执行进程、恢复默认配置，并回归旧链。
