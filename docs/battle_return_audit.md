# 原版战斗返回链审计

本页只记录可从原始脚本、`analysis/hermit_game.exe` 指令及调用方交叉核对的事实。编译器名表的 `TACTGAMEEND`、`GETTACTRET`、`PUTTACTRET` 是原始名称，不单独证明胜负、战果字段或周历语义。地址均为原版 EXE 虚拟地址；脚本偏移是对应 BIN 的文件偏移。

## 1. 战术脚本出口与 opcode 112、147、148

| 来源 | 原始记录/调用边 | 已证实的动作 | 尚未证实 |
|---|---|---|---|
| `T0005.BIN` block0/sub20 `0x2AE8` | `70 00 10 00`；操作数 `v0x0, 16, 40`。之前是 `NETKEYWAIT`，之后仍有 `NETKEYWAIT`、`TACTANIMPLAY` 和 `END`（`0x2B34`） | 脚本显式执行名为 `TACTGAMEEND` 的 112；它不是字节码块的最终 `END` | 后两个 cell 在 112 处理器里未被读取，不能把 16/40 当作结果码 |
| `T0048.BIN` block0/sub1 `0x480`、`0x5C0` 等 | 多个分支先写 `UNITWK`、执行 `TACTPLAYEREXIT`、`NETKEYWAIT`，再执行 112 并跳往共同出口 | 112 可以是多个脚本分支的会合点；脚本出口包含独立的单位工作区写入 | 不能把这些 `UNITWK` 字段自动解释为角色持久档或战果字段 |
| `4CE8F0` case `0x70` → `42D960` → `4978C0` | 汇编 `42D983–42D9C7` 只从 `instruction+4` 取首个 cell，经 `4C1EB0` 求值，传给 `4978C0`；随后置 VM `+0x92E0=1`，处理器返回状态 4 | `4978C0` 设置 ScriptWork `+0x2490/94/98/99/9A/9C`，以参数为计时分母；`497AA0` 按帧更新并完成该状态；`4CE8F0` 的状态 4 读取 `+0x92E0` | 112 不直接写角色档、战果分支或日历；`+0x92E0` 的解除/整个退出路径尚未闭合，不能视为已完成战后事务 |
| `454CF0` case 2–5 | case2 调 `4CE8F0`；case3/4 用 `497C50` 检查 ScriptWork `+0x249A`，必要时 `497980(60)`；case5 执行战术任务收尾 | VM、计时工作区和任务收尾是不同层级；不能只凭本地 `winner` 越过脚本/任务 | case5 到战果任务 `4BD660/4BAA90` 的上层调度边留待 §2 |
| `4CE8F0` case `0x93`/`0x94` → `4C4840`/`4C4950` | 汇编 `4C4863–4C4923` 与 `4C4973–4C4A2A` 均读取 3 个 cell，经 `4C1EB0` 求值，再以首个调用实参分别为 0/2 调 `40D390` | `40D390` 使用 `DAT_007A49FC+0x1A98` 的资源表：校验 20×120 索引、可选 64 个槽位、调用对象虚表 `+0xB4`；`4BDAC0` 战果展示也调用它。这个调用链没有可见的战果字段读写 | 原始编译器名称与实际处理器行为相冲突；在找到其它消费者或运行时证据前，147/148 不可用作战果读写契约 |
| `T0080.BIN` block0/sub7–9、block1/sub4–9 | 9 个表面上的 148 均为 `94 00 04 00`，后 4 字节为零数据池头；例如 `0x2080` 和 `0x3010`。`analysis/script_disasm` 将它们列作 `PUTTACTRET adv=4` | 原生 148 处理器会读取 `instruction+4/+8/+12` 三个 cell，这些记录的声明长度却只有 4 字节；语料扫描未发现 147 | 这些记录的可执行性/容器含义未证实，不可算作 9 次真实战果写入；`T0080` 子记录解析器可能把非执行占位记录当成指令 |

`T0005.BIN` 的 `0x2AE8` 原始前 16 字节为 `70 00 10 00 00 00 00 00 10 00 00 20 28 00 00 20`。这同时证明 `adv=16` 和后两个立即数确实存在于脚本数据中，并不证明处理器消费它们。`4C1EB0` 的 type 0 为 VM 变量引用、type 2 为立即数；故首 cell `v0x0` 的实际值必须由当时脚本状态决定，不能由文件静态推出。

当前可作为后续样例输入的只是“脚本在上述偏移执行了 112”的来源事实。它尚不是可应用的胜利、战果分支或周推进请求。后续 §2 须继续闭合战术任务退出与战果任务调度，§3 须闭合字段和周结算；在此之前任何转接层都保持待定。

## 2. 战果任务初始化、展示与退出分支

`4C1AA0` 的分支判定和调用顺序已用 `analysis/hermit_game.exe` 的 `0x4C1AC9–0x4C1C5D` 汇编复核；下表中的 0/1/2 是对象 `+0x30` 的原始数值，不是胜/负标签。

| 函数/时点 | 原始条件及调用顺序 | 可确定的结果与限制 |
|---|---|---|
| `4BD660 → 4BAA90`，战果任务初始化 | 加载 `data/TacticsResult/TacticsResult.bin`，清对象 `+0x34` 起 `0x198` 字节。仅当 `DAT_007F4491==1 && DAT_007F4505==0` 时将 `+0x32=1` 并跳过 `4BBCC0`；其余情况调用 `4BBCC0` | 战果准备并非总执行；不能把初始化阶段的计算称为退出时发奖 |
| `4BBCC0`，条件性准备 | `4BD210 → 4BCA40 → 4BBD40`，之后置对象 `+0x32=0`；若月 `DAT_007A528E==15` 且周 `DAT_007A5290==4`，改为 1 | `4BCA40` 读取学园/场次表并填入对象 `+0x140` 起的候选记录，发生在战果任务初始化；不是战果退出时的持久奖励写入 |

| `4BD870`，所有分支共有 | 装载 `data/AllResult/AllResult.bin`；重置 `DAT_007E1180` 等战果全局量；`4D0860 → 4BFFC0`；模式 0 调 `4C00C0`，非零且 `DAT_007F4505!=0` 调 `4C0350`；计算并钳制 `DAT_007A511C`，创建全战果动画 | `4C00C0` 从参与者/分组及成绩找出 `DAT_007E1180` 等展示用目标；模式分支的展示计算不等于学园周推进 |
| `4C1AA0` 分支 0（常规条件：模式 0、非月 15/周 4） | `4BDAC0 → 4C1350 → 4D0750 → 422360(5)`；对 `DAT_007E1180` 指向的 `0x124` 字节角色记录中的 `+0x120` 短整数字段加 1 并钳到 0..5；启动 `CH003.ybc` 入口 7、任务 6 | 有角色回写与展示/跳转，**没有** `4D3510`；字段用途及索引合法条件留给 §3，不能称为“普通胜利后一周” |

两个可复查的控制流样例：若 `DAT_007F4491=0, DAT_007A528E=14, DAT_007A5290=4`，分支键为 0，先执行 `4BD870` 的模式 0 展示计算，再走 `4BDAC0/4C1350`，不进 `4D3510`。若仅把月改为 15，分支键为 2，仍先执行 `4BD870`，再走 `4C1350` 与 `4D3510`；两条路径不应合并为按胜负分派。模式 1 的初始准备还有 `DAT_007F4505` 的额外门槛，和上述两条均不同。

EXE 内的虚表 `0x59A430=[451670,451630]`、`0x5A0DFC=[4BD660,4BD620]`、`0x5A0F74=[4C1AA0,4C1A60]` 分别由战术任务、`TacticsResultTask.cpp`、`AllResultTask.cpp` 的构造函数安装，解释了为何普通文本 xref 没有直接调用。控制器 `49E2B0` 从 `DAT_007A4A00+0x30` 读状态并跳转；EXE `0x49E4D3` 的 25 项原始跳表确认状态 11 → `49E3A8 → 4BD6F0`（战术结果构造）、状态 10 → `49E36E → 4B9120`（准备任务）、状态 12 → `49E37E → 4C1D30`（总战果构造）。`451670 → 451A60 → 4539B0 → 454CF0` 构成战术任务更新中的 VM 调用路径；其退出逻辑在部分条件下发出 `439E30(11)`。`4BD660` 战术结果任务结束时发出 `439E30(10)`；准备任务 `4B8FF0` 若 `DAT_007A5296==DAT_007A5298` 则发出 `439E30(12)`，否则处理下一场并发出状态 16。

因此已证实的主干是“战术任务 → 战术结果 → 准备/场次循环 → 全战果”，**不是**直接从战斗胜负跳到 `4C1AA0`。尚未闭合的是具体 `TACTGAMEEND` 首 cell/VM 忙状态怎样促使战术任务退出，以及一条 `T0005.BIN` 运行路径如何满足状态 11 和准备任务的场次完成条件。不能把这条脚本样例直接标为可应用的角色/周历事务。

## 3. 角色记录与周结算边界

以下偏移均相对角色记录基址 `DAT_007CF34C + character_id * 0x124`。`character_id` 是原版数组索引，不得由 Godot 阵容位置或显示名推断。`4C1350` 和 `4D3510` 的关键访存已与 EXE 汇编交叉核对：`4C1428` 读取 `DAT_007AAA22`，`4C151D` 读取 `DAT_007A5210`，`4C16AA/4C16ED` 读写 `DAT_007CF423`，`4C18EE` 调 `4BF9E0`；`4D352D–4D35CF` 是周数进位、参与者循环及两个整理调用。`4C1B71–4C1BA8` 证明上一节的目标字段是 `+0x120`，并非 `+0x100`。

| 写入/消费者 | ID 来源、范围及字段 | 边界与后续影响 |
|---|---|---|
| `4C1350` 参与者集合 | 5 组×最多 4 位的 `DAT_007AAA22` 非负角色 ID；本场 `DAT_007A5210[0..DAT_007A5260)` 也给出角色 ID。函数整理为组内、全场及未在组内三类列表 | 源数组是 ID，不是持久档本身；无效/缺失 ID 的安全范围不能由此函数证明，重制版必须显式验证 |
| `4C1350` 计数 | 全场角色 `+0xD7 + type` 的字节计数，`type` 读自 `DAT_007E17EE[id*0x4A0]`；若当前值不等于 100，则加 1 并钳至 0..99 | 原码只特判 100 的哨兵，不能假设任意大值或负 ID 都安全 |
| `4C1350` 历史 | `week_index=(month-4)*5 + week-1`；每组角色在 `+0x24 + 3*week_index` 写入 1 或 2（由组状态 4/2 决定）及两个关联字节；仅在本场但不在该组列表者写入 3 | 由已知 `+0xD7` 计数区反推，三字节历史记录至多安全覆盖 `week_index=0..58`（月 4/周 1 到月 15/周 4）；月 15/周 5 的索引 59 会触及 `+0xD7`，不能让任意月周写入此区。原版场次是否禁止该边界尚待查 |
| `4BF9E0 → 4D3960` | 依据非组内角色、组员、组长及场次名单的配对，写 `DAT_007D3D71[id_a*0x44+id_b]` 关系字节，钳至 1..100；`4D3960` 对大于 100 的传入 ID 减 55 | 配对是有序的，某些路径双向调用；其正负调整并非单一“所有参战者友好度+1”，也不属于角色记录的 `0x124` 字节 |
| `4C1AA0` 分支 0/2 | `DAT_007E1180` 给出展示选中的角色 ID，该角色 `+0x120` 短整数加 1，钳至 0..5 | 先由 `4BD870 → 4C00C0` 挑选；若没有合法 ID，原码中 `0xFFFF` 初值可能导致越界，必须先核对场次不变量，不能无条件照搬 |
| `4D3510` 周结算 | 周 `DAT_007A5290 += 1`，达到 6 时月 `DAT_007A528E += 1`、周置 1；清 `DAT_007A55FA`、`DAT_007A4E62`；对本场 `DAT_007A5210[0..DAT_007A5260)` 的每个 ID 调 `4D3AA0`；依次调 `4D31F0`、`4D34A0`；末尾置 `DAT_007A55F6=11`、`DAT_007E11A0=0` | `4D3AA0` 按新月周、七属性、属性和及至多三项先决值给角色 `+0xF9..+0x116` 置解锁标记；`4D31F0` 检查 360 个道具状态/归属，`4D34A0 → 4D33A0` 整理角色持有状态。周结算不是独立计数器 |

`4D3510` 除结果分支 2 外，还由 `49F4E0` 调用，后者随后启动 `CH001.ybc` 入口 8。这是另一条周推进路径，并不经过 `4C1AA0` 的结果分支。它的上层调度仍需核对，因此不能据此猜测每次战斗都推进一周。

目前可确定的是写入目标、调用顺序和主要范围；尚未证明脚本首 cell 与战果模式/角色 ID 的对应关系，也未验证所有原版场次均满足历史窗口、选中角色及库存不变量。故分支 0/2 可以作为**审计过的原版路径**，但尚不可作为对任意 Godot 战斗自动应用的持久事务契约。实现阶段应先建立终局事实和脚本来源双轨；只有数据映射、字段语义及完整副作用闭合的特定样例才可提交事务。

## 4. `T0005.BIN` 到战术任务退出的条件审计

`451BF0 → 454FA0` 装载 `data\\Tactics\\Script\\%s`；`454FA0` 通过 `451D10` 取得 `DAT_007F4488` 并查 `0x60BC78` 指针表。原始 EXE 的第 5 项指向 `0x59A3A8`，内容 `t0005.bin`，所以场景 ID 5 确实选择当前脚本样例，而不是仅凭文件名猜测。`T0005.BIN` block0/sub20 的 `0x2AE8` 为 112，`0x2AF8` 仍有 `NETKEYWAIT`，`0x2B14` 仍有 `TACTANIMPLAY`，`0x2B34` 才是 `END`。

| 边/条件 | 原始指令与结论 | 是否闭合 |
|---|---|---|
| 场景 5 → `T0005.BIN` | `451D10` 返回 `DAT_007F4488`；`454FA0` 以它索引 `0x60BC78`；第 5 项 `0x59A3A8` 是 `t0005.bin` | 是，装载关系已证实 |
| 112 → VM 等待 | `4CE8F0` case `0x70` 调 `42D960`；汇编 `42D9C4–42D9C7` 置 `VM+0x92E0=1`，返回状态 4；`4CE8F0` 状态 4 只有该标志为 0 才回到状态 0 | 是，进入等待已证实；不等于战术任务退出 |
| VM 等待 → 后续 `END` | 反编译语料中唯一显式清 `VM+0x92E0` 的 `4CDF80` 没有直接调用或地址指针引用；其它间接/批量写入和运行时调度仍待查。`454CF0` 仅在 `4CE8F0` 返回 0 时从内部 case2 进入后续 case3–5 | **否**；不能证明 `0x2AF8/0x2B14/0x2B34` 在 112 后实际执行 |
| `454CF0` case5 → 退出演出 | 当内部 `+0x4C==1` 时置战术任务 `+0x171/+0x172=1`；`453F10` 相位 5 等待 `+0x171` 后继续，相位 19 淡出完成或相位 20 时返回 1；`4539B0` 将该返回值作为循环退出条件。汇编 `4539FB–453A00` 和 `454798–4547A8` 复核返回值，而非采用反编译器的 `void` 返回类型推断 | 条件边已证实，但未证明 112 必然到达 case5 |
| 战术任务退出 → 状态 11 | `451670` 中 `451A60` 在任务 `+0x34==2` 时调用 `4539B0`；非网络、非特殊场景分支最终执行 `439E30(0xB)`（汇编 `451958–451963`）。场景 ID 5 不在 `0x4C..0x52` 特例集；网络、退出标志、后继场景另有分支 | 条件边已证实；不是任何 112 都无条件进入 11 |

因此 `T0005.BIN:0x2AE8` 仍只是一条真实的**脚本侧请求**。它与场景 ID 5 的装载关系，以及战术任务的条件性状态 11 出口均已定位；中间的“112 等待解除/脚本或任务转相位”缺口必须保持 `unresolved`。当前 Godot `battle_exit_requests.json` 不应带有“已到状态 11”或“可回写角色”的标记。

## 5. 状态 11→10→12/16 与准备期场次门槛

控制器 `49E2B0` 在 `49E304` 通过 `0x49E4D3` 的原始跳表分派，构造函数安装的虚表再选择任务更新函数。`prototype/data/battle_state_chain.json` 记录以下地址和两条**分支条件见证**；`tools/tests/test_battle_state_chain_evidence.py` 直接对原始 EXE 的跳表、相对调用和比较/计数指令作断言。它们不是某份已运行存档，也没有把 `T0005.BIN` 的 112 误标为已到状态 11。

| 原始状态 | 控制器 case → 构造 → 更新 | 更新结束后的可证状态 |
|---|---|---|
| 11 | `49E3A8 → 4BD6F0 → 4BD660` | `4BD660` 在 `4BAA90`、条件性 `4BAB60` 与任务收尾后，于 `4BD6C4` 请求 10 |
| 10 | `49E36E → 4B9120 → 4B8FF0` | `DAT_007A5296==DAT_007A5298` 时 `4B901F` 请求 12；否则完成下面的准备写入，计数加一，于 `4B90DA` 请求 16 |
| 12 | `49E37E → 4C1D30 → 4C1AA0` | 进入 §2 所审计的总战果分支；并非战术任务直接抵达 |
