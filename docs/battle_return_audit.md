# 原版战斗返回链审计

本页只记录可从原始脚本、`analysis/hermit_game.exe` 指令及调用方交叉核对的事实。编译器名表的 `TACTGAMEEND`、`GETTACTRET`、`PUTTACTRET` 是原始名称，不单独证明胜负、战果字段或周历语义。地址均为原版 EXE 虚拟地址；脚本偏移是对应 BIN 的文件偏移。

2026-10-02 的原版 VM 指令执行纠正了早期分派编号误读：`4CE8F0` 的内层 switch 使用 **opcode−5**。早期把 switch case 直接当作脚本 opcode，误记了 112、130、147/148 的消费者。本页对应记录已修正，新增逐指令执行证据见 §17；旧采样文件保留原字节，不追溯改写。

当前可作为后续样例输入的只是“脚本在上述偏移执行了 112”的来源事实。它尚不是可应用的胜利、战果分支或周推进请求。后续 §2 须继续闭合战术任务退出与战果任务调度，§3 须闭合字段和周结算；在此之前任何转接层都保持待定。

## 3. 角色记录与周结算边界

以下偏移均相对角色记录基址 `DAT_007CF34C + character_id * 0x124`。`character_id` 是原版数组索引，不得由 Godot 阵容位置或显示名推断。`4C1350` 和 `4D3510` 的关键访存已与 EXE 汇编交叉核对：`4C1428` 读取 `DAT_007AAA22`，`4C151D` 读取 `DAT_007A5210`，`4C16AA/4C16ED` 读写 `DAT_007CF423`，`4C18EE` 调 `4BF9E0`；`4D352D–4D35CF` 是周数进位、参与者循环及两个整理调用。`4C1B71–4C1BA8` 证明上一节的目标字段是 `+0x120`，并非 `+0x100`。

| 写入/消费者 | ID 来源、范围及字段 | 边界与后续影响 |
|---|---|---|
| `4C1350` 参与者集合 | 5 组×最多 4 位的 `DAT_007AAA22` 非负角色 ID；本场 `DAT_007A5210[0..DAT_007A5260)` 也给出角色 ID。函数整理为组内、全场及未在组内三类列表 | 源数组是 ID，不是持久档本身；无效/缺失 ID 的安全范围不能由此函数证明，重制版必须显式验证 |
| `4C1350` 计数 | 全场角色 `+0xD7 + type` 的字节计数，`type` 读自 `DAT_007E17EE[id*0x4A0]`；若当前值不等于 100，则加 1 并钳至 0..99 | 原码只特判 100 的哨兵，不能假设任意大值或负 ID 都安全 |

`4C00C0` 的展示目标选取已进一步按原始字节落实为纯选择器（`prototype/sim/all_result_recipient.gd`；来源样例 `prototype/data/all_result_recipient_evidence.json`）。`4BD870:4BD8ED` 将目标 ID 初始化为 `0xFFFF`、最大比较值设为 0；只在模式 0 的 `4BD9D0` 调用 `4C00C0`。它按 5 组×4 槽遍历 `DAT_007AAAE0` 的非负**参与者索引**，再经 `DAT_007A5210` 取原版角色 ID，以角色记录 `+0x20` 的 32 位值与当前最大值作严格大于比较，且候选 ID 必须 `<13` 才更新 `DAT_007E1180`。同分保留先出现者；所有值不大于 0 时保留 `0xFFFF`。原版在 ID 上界检查前已有记录读取，因此重制选择器先验证索引、ID 与数据齐备性，任何无效候选都返回未解析而非部分选中，更不会写入 `+0x120`。

这两张表的来源也已追到 `4D3E90`：在角色 ID 非零、尚未入表且 `<101` 的条件下，`4D3F0F` 将 ID 写到 `DAT_007A5210[current_count]`，`4D3F39` 将同一个 `current_count` 写到传入组/槽的 `DAT_007AAAE0`；`4D3F4F/4D3F66` 还将原始角色 ID 写到 `DAT_007AAAB8/DAT_007AAA22` 的组/槽。因此 `DAT_007AAAE0` 组槽索引绝不能直接解释为角色 ID，而 `DAT_007AAA22` 组槽存的确实是原始 ID。`49E930` 与 `49EE30` 的初始调用均按 `(ID,组,槽)=(3,0,0),(4,0,1),(9,0,2)` 传参。这只给出**有条件的初始化来源**，不是场景 5 结束时的最终阵容；脚本、存档或后续增删仍可改变列表。当前 Godot 战斗布阵没有这些原版 ID，场景 5 到状态 12 的同一运行实例亦未证实，故上述样例明确不授权持久回写。

`4D3510` 除结果分支 2 外，还由 `49F4E0` 调用，后者随后启动 `CH001.ybc` 入口 8。这是另一条周推进路径，并不经过 `4C1AA0` 的结果分支。它的上层调度仍需核对，因此不能据此猜测每次战斗都推进一周。

目前可确定的是写入目标、调用顺序和主要范围；尚未证明脚本首 cell 与战果模式/角色 ID 的对应关系，也未验证所有原版场次均满足历史窗口、选中角色及库存不变量。故分支 0/2 可以作为**审计过的原版路径**，但尚不可作为对任意 Godot 战斗自动应用的持久事务契约。实现阶段应先建立终局事实和脚本来源双轨；只有数据映射、字段语义及完整副作用闭合的特定样例才可提交事务。

## 7. 只读运行轨迹采集与启动期观测

`tools/battle_runtime_trace.py` 将上述同实例取证要求落实为 Windows 只读采集工具。进程句柄只申请 `PROCESS_VM_READ | PROCESS_QUERY_INFORMATION`；Win32 函数均显式声明指针宽度安全的参数/返回类型，不注入、不打断点、不写内存或存档。自动选择时出现多个同名进程会拒绝并要求显式 PID；指定 PID 也必须通过工作区原版 EXE 路径核对。它在固定基址先检查 MZ、可用时检查 PE32，再逐个比较六处原版代码/任务记录探针。脱壳后的原版进程及现有审计映像的 PE 头都可能被壳覆盖，因此 `pe_header_unavailable` 单独记录，不能声称完整 PE 校验通过；仍必须全部通过来源字节探针，来源映像 SHA-256 也会写入元数据。这只是选定探针的一致性，不是全映像一致性证明。

用法（先正常启动原版；输出目录需存在，输出文件必须是新文件）：

```text
python tools/battle_runtime_trace.py --pid PID --seconds 30 --interval-ms 50 --out analysis/scene5_trace.jsonl
python tools/battle_runtime_trace.py --pid PID --once
```

采集请求标志/分派槽、月周、当前/总场数、任务/场景/模式、参与者 ID、五组原始 ID 与参与者索引、首场配置/名单。仅在分派槽为 16 时读取经虚表核对的战术任务和 VM，避免在其它槽追随旧任务全局。战术字段包含脚本控制相位、结束标志、结果选择参，以及 VM 子记录/代码指针、PC、等待状态和工作区等待标志。旧 schema 1 将后一字段误名为 `wait112`；schema 2 改为 `script_work_wait`，旧文件不改写。场景 5 下先逐字节比较整个加载的 `T0005.BIN`，再用原版容器偏移及 VM 的子记录/代码两个指针同时识别 block/sub；2/5/8/11/14 只标为终结**候选**，20 不标终结。未知文件或指针不匹配保持 `unresolved`，选中子记录不证明来自 `4337F0` 的某一调用点。

每份样本在结束时反向复读所有已采集片段；读取失败、长度不足、表人数越界或端点变化会丢弃整份观测并记录错误。端点相等仍**不是原子快照**，不能排除中途变化后恢复、释放后复用同址或轮询漏掉短状态；PID、进程创建时间、trace ID 也不能替代任务实例生命周期及调用来源证据。`controller+0x30` 由 `439E30` 写入，配套 `+0x2C` 请求标志，故命名 `request_dispatch_state`，不得将读到 11/12 等同于对应任务已经完成。所有观测始终 `authorizes_persistent_write=false`，工具不会生成 Godot 可应用的事务。
