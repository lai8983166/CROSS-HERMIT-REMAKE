# 原生战斗等待窗口（进行中）

此工具把原游戏中的短等待观察接到已验证的菜单→职务室→学校→真实战斗退却路径。
它保留当前原生事件、线程/TLS/PTD、原调用栈及内核等待返回的联系；ETW 和暂停快照
不替代完整用户态指令、CPU/RAM/ABI、累计轨迹和实际资源/PTD 清理证明。
`connect-terminal-wait-and-battle-exit` 的正式任务仍按原标准验收。

## 执行与接续

使用当前 F 盘 2 vCPU/4 GiB 后台 Windows 客体。每次冷启动重新核验客体 UUID、
启动 UTC、资源配置、时钟、D3D8 和输入隔离。宿主机不启动交互游戏、不发送输入。

先用 `devtools.isolated_vm_battle_wait --label <新的小写标签>` 在 startup 采集约
150 ms 窗口。独立解码入口为：

```bash
.venv-audit/Scripts/python.exe -B -X utf8 -m devtools.isolated_vm_battle_wait_decode \
  --source-label preflight-v1-20261109 --label new-preflight-proof --diagnostic-only
```

显式诊断模式不把未采到的 CRT 退出返回点补成成功。客体命令返回 2、宿主命令保持
非成功，报告中另列 `long_capture_preflight_passed`：它只表示当前采集能力已得到
至少三次不同成功等待、完整原始事件配对和当前所有者验证，不是正式功能验收。

长路径必须提供这份有限能力报告的明确路径及 SHA。调度器重新核对报告、原来源、
完整 ETL、六项预检验证依赖、五项采集依赖，以及同一次客体启动和资源配置。验证器发生
变化时先对保留来源生成新证明；采集器变化时不能沿用旧采集能力报告。输入和窗口
稳定后只启动一个代表案例，不能让两个长任务重复发现相同问题。

```bash
.venv-audit/Scripts/python.exe -B -X utf8 -m devtools.isolated_vm_battle_wait \
  --label new-battle --phase battle_retreat \
  --preflight-proof <本轮等待预检报告路径> --preflight-sha <报告完整SHA256> \
  --retention-proof <本轮线程保留预检来源路径> --retention-sha <来源完整SHA256>
```

线程保留短预检使用同一入口的 `--phase retention_preflight`，只观察当前原生启动，
不发送剧情或菜单输入。两个前置能力报告必须属于同一次客体启动，并且各自执行层
仍为相同字节。长采集开始后不得修改这些执行文件。

输入仍由原有受限后备执行，原确认动作的第二次左键状态查询触发采证；其后继续执行
原最后一次状态守卫、坐标核对及按下/释放，不改点击值或写游戏结果。共享可重入锁
只串行化原输入守卫的暂停采样和新窗口采样，作用域结束必恢复；不锁住宿主输入。
全部事件、线程句柄只针对已认证客体中的当前原进程。

新适配器另在实际 `SendInput` 调用前后记录 `GetSystemTimePreciseAsFileTime` 与完整
原 INPUT 包。原输入回执的普通时钟字段原样保留，不以偏移量修正成希望的顺序。
解码时显式选 `--verification-version 2`，验证实际包、调用结果和精确时间包络；
原保持时长、输入边沿、守卫与查询仍走既有严格检查。

完整前缀另用 `devtools.terminal_worker_retention_verification_v2`，提供 `--source`、
`--source-sha`、绑定该来源与客体启动的 `--guest-modules` 清单和全新的 `--out`。
它离线验证全份输入历史及所有保留状态，不需要再次启动游戏；进程返回 0 也只表示
这份有限观察验证通过，完整重放、资源/PTD 清理仍按各自真实证据判断。

## 学校构造阶段的观察器修正

首个完整前缀在 908.891 秒时因 `DuplicateHandle` 的错误 6 停止，尚未发送学校或
战斗输入。已成功保留学校 GROUP，随后失败的具体节点没有被旧观察器写入来源，
因此不能把失败归因为一个已确定的节点、退役竞争或资源失效。

原字节显示，基础构造器尚未初始化 `+20/+24`，节点可先注册到管理器链，随后才创建
原 CRT 线程并写入句柄/TID。旧实现还在恢复线程后才复制快照中的句柄。
`terminal_worker_retention.py` 先以同一线程句柄核对 PID/TID，再暂停 MAIN 与完整有界
客体线程集合，在保持暂停时读取注册图、TLS 并复制真实 worker 句柄，结束时只撤销
自己的暂停计数。

缺少原回调祖先的构造中节点仍按原字节保存，标为 `pending_callback_ancestry`，
不复制它尚未认证的句柄。首次保留必须同时具有 `421F8A/56E183` 和真实 TLS；
任何部分祖先不能伪装成 pending。既有 worker 的 CRT 尾段允许祖先自然退役，但
不能据此宣告 PTD 清理。输入目标始终要求已保留的当前线程及完整 TLS/祖先。

独立适配器只在固定旧验证器 SHA 下修改三个精确 AST 条件，保留完整原图、上下文、
TLS、输入和来源核验；pending 不会被后来同 node/TID 的线程身份追认为已构造。
首个失败行及实际 API 参数单独保存，不跳过真实句柄或事件验证失败。

下一代表前缀在 653.703 秒保存到另一处过渡：ADV 原线程/TID、句柄及事件未变，
虚表变为 `594A54`，flags=4，线程已不在当前暂停集合，MAIN 栈含 `421ACE→42182F`。
原 ADV 在回调中主动析构，再经原 worker 退出；MAIN 先 `Sleep(2)` 和
`GetExitCodeThread` 轮询，然后关闭节点事件、卸链。旧观察器要求虚表始终相等，
因此在这段合法状态变化中停止。旧失败来源没有当时的退出查询和调度器局部变量，
不能补签为成功。

`terminal_worker_retention_v2.py` 保留原节点和历史派生类型，对虚表变化记录
`retained_vtable_transition`、原保留句柄的实际查询、调度器原始栈及必要 worker 栈。
它只收集尚待分类的过渡，不把任意虚表变化宣称为已验证；真实句柄或事件身份变化
仍拒绝。新独立验证器目前只认证有此前真实 TLS 来源、基础虚表 `594A54`、flags=4、
实际退出查询为 0、原调度器参数和栈关联全部吻合的分支；其它过渡保持拒绝。
该分类不等于完整析构指令、事件关闭或 PTD 清理。输入目标不享受过渡豁免。
采样保存签名另含保留状态，确保第一次真正保留的行不会因图/VM 未变而漏存。

第三次前缀在暂停集合前后不一致时停止；旧失败现场没有两份线程清单，不能据此断言
是哪一条线程创建或退出。`terminal_worker_retention_v3.py` 仅对这类清单变化重试：
先完整恢复本次自有暂停，再重新枚举，最多五次、后续尝试必须在 500 ms 预算内开始。
每次失败保留前后清单及恢复记录；PID/TID、暂停、上下文、恢复或关闭失败不享受重试。
独立验证仍要求最终快照为完整稳定集合，不能把重试拼成同一时刻的快照。

第四次前缀在 1.375 秒即因缺少工厂快照停止，并记录窗口激活失败、Job 应急清理。
原自动激活位于工厂采样前，可能占用短暂构造窗口。新增 `terminal_factory_focus.py`
只推迟自动激活，直到同一原进程/句柄的原工厂和就绪快照都实际返回；不补造快照、
窗口或激活成功。固定原函数和文件 SHA 后仅替换一处运行类选择，作用域退出恢复
观察钩子并重新核对字节。原激活方法、成功回执、输入与验收条件保持不变。

最新启动预检使用与长路径相同的聚焦运行类，但不发送菜单输入。实际取得工厂
0.812 秒、就绪 1.500 秒、随后激活 1.515 秒的原始来源；规范 JSON 摘要、原祖先、
当前所有者和钩子恢复通过主 Agent 独立复核，八帧线程保留也通过。该来源未触发
线程清单重试或 ADV 退役分支，不把对应单元测试称为原生分支验证。

2026-11-09 短预检已观察 38 个真实等待快照，完整原 ETL 离线读取 123,180 条记录，
配对得到 10 次不同的原等待成功返回，0 丢失；另一次新鲜启动的 8 帧线程保留预检
通过独立原上下文/图/TLS 复核。前者仍缺少严格 CRT 退出采样，后者不含学校 pending
构造分支。两者只授予有界采集能力，不算正式战斗退出或资源/PTD 验收。

## 证据与边界

窗口保留原 `42240D` 等待帧和相应调用者：`453CB5/453CD3/453CDD`、`451758`、
`451796`。每份成功观察必须完整落入同一线程唯一一对实际 NtWait 进入/返回事件，
核对原 Win32 事件/超时及 Nt 参数、实际 DLL 指令、当前 FS/TEB/TLS/PTD 和注册图。
暂停上下文中的 EAX 不充当系统调用返回值，返回值来自后续原 ETW SysCallExit。

场景结果读取原 `4539B0` 帧 `-8`、分派器 `451A60` 帧 `-8`、回调 `451670` 帧
`-0C`。十轮尾等待还要求十个不同调用分别有原计数 `0..9`；不能由末计数推补漏帧。
`4967B0` 的记录门使用原 signed byte，前后门值相同不等于已观察中间每条指令。
原输入记录的完整来源及规范 JSON 摘要单独绑定，不把时间接近当作输入因果证明。

内核日志采用明确的新预算：0x92 标志、顺序文件、64 KiB 缓冲、4–8 个缓冲区，
完整 ETL 必须小于 64 MiB。窗口最多 3 秒和 768 份等待快照；来源展开不超过
8 MiB、压缩不超过 2 MiB，所选事件至多 16,384 条且压缩不超过 512 KiB。
独立解码完整读取 ETL、保留原头/载荷/CPU 归属及全流摘要；缺帧、重叠调用和超限
不靠截断或猜测配对消除。ETL 全量只在 F 盘本地保留，Git 保存必要小报告、原字节
摘要和复现代码。一次合法前缀历史另存压缩来源，窗口引用它，不复制整段历史。

## 输入窗口前置准备与日志初始边界

第五次前缀已经到达真实退却确认。实际 OS 按下和释放均返回 1，但新观察器在第二次

调用补签成已验证的退却。完整失败源和当时执行版本保留，未沿用为成功来源。

`terminal_battle_wait_window_v2.py` 在固定原 v1 文件 SHA 后，按唯一
`r['before']=self.snapshot()` 边界拆分原 `begin`。PE、导出、TLS 实现解析先执行，

随后执行原样的当前所有者快照、事件验证、线程复制及 ETW 启动尾段。输入期限仍为
11 秒，等待窗口仍为 3 秒，不延长两者来掩盖准备耗时。

新短预检使用实际原游戏 worker，另一个观察线程调用真实启动尾段，主线程同时轮询，
但不发送输入。准备 9.004 秒发生在观察前，真实触发 10.039 毫秒，并发观察在
0.125 秒完成。此测量只说明准备已经移出关键输入窗口，不表示完整剧情同比加速。
长采集门同时核对全部五项生产依赖、独立证明、当前客体及实际并发时序；任何生产
依赖变化都要求新短预检，验证层变化则先对保留来源离线复核。

该短来源包含 88 帧，首帧处于日志启用后的初始未配对范围。v2 独立验证只允许它位于
trace begin 之后、第一条实际 SysCallEnter 之前，且前缀全为原 CSwitch、完整快照
严格落在唯一原线程切出/切入区间。此帧明确标为
`initial_before_first_recorded_syscall`，不计为成功；中间缺失、跨越首个 syscall 或
已有早期 syscall 的情况仍拒绝。原 v1 拒绝报告保留。

同份 ETL 完整读取 53,198 条记录后，16 次不同等待有完整真实进入/返回对；默认严格
窗口验证通过，原事件与栈另经独立重算。这里的严格窗口检查不等于完整原生状态/
指令/ABI 重放或 PTD 释放；正式任务仍须完成剩余证据。没有为解决此验证边界重采游戏。

线程退出码 0、窗口关闭或 Job 为空不能证明 PTD 已释放。后续仍须证明实际 CRT
分支、嵌套分配释放、成功 TLS 清零、原事件关闭及节点卸链，并区分原线程句柄和
观察器副本。原保护父进程不兼容的 #DB relay 继续禁用。
