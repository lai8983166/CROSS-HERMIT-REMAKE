# REA 等待链复核与路线止损

2026-11-13：本轮实际使用 REA 重新分析原镜像，并重新核查验收合同。
结论是**停止扩建“子 VEH 停点→搬运完整原机现场”的路线，转回原指令执行器的当前所有者接通**。
替代路线仅具备开展有限实现的依据，尚未通过原生准入；正式仍为2/8。
本轮没有运行游戏、VM、原生等待探针、截图或桌面输入，没有安装驱动或修改系统设置。

## 实际 REA 调用

在F盘隔离安装固定 `rea-agents@6.4.0`，复用 Ghidra 12.1.3 和已有 JDK。
一个真实 MCP 会话完成31次工具调用，包含7个函数的汇编/伪代码、调用关系、交叉引用及
4份字节读取；全部返回成功。会话150.562秒，含146.140秒首次导入；正常关闭，server exit0。
源镜像 SHA-256 保持 `588b4288e4c737dc489d2b9bc0652cca85e3d668b1784942ef4b4bda916f1005`。
入口和214个IAT名称来自既有分析，属于提示，不能算作REA的新发现。

主审对743个汇编地址/助记符重新解码，核对22处关键操作数；独立审查不导入主审实现，
另核6个函数的458条指令、20处关键操作数。两者均核对REA读取的654字节与原镜像相同。
真实调用原件、工具schema、种子及环境锁定文件存于
`analysis/terminal-rea-wait-chain-session-v1-20261113.zip`；独立结论见
`analysis/terminal-rea-chain-independent-review-v1-20261113.json`。

## 重新确认的调用链

| 位置 | 原代码行为 | 对后续工作的含义 |
| --- | --- | --- |
| `4539FB→453A00` | 调用453F10，把EAX写入调用者栈的 `[EBP-8]` | 场景结果在等待前已产生，必须保留其原来源 |
| `453CB0→422360` | 传delay0；原节点置让出标志、Reset节点事件、Set管理器事件，再等待节点事件 | 需要真实manager/node事件、锁与worker所有者 |
| `422407→42240D` | 调用WaitForSingleObject后比较ESI与ESP | 这是栈平衡检查，原代码没有检查等待返回码；验证器仍必须独立拒绝失败等待 |
| `42241C→4225A0→422431` | 清除节点10000h标志，再RET 4 | 正常ABI路径没有新的必经文件事件可以用作停点 |
| `453CB5` | `cmp dword ptr [EBP-8],0` | 首次读取保留的场景结果；它不是读取Wait API的EAX |
| 零结果 | `453CE4→4539CD` | 继续原循环 |
| 非零结果 | `453CC4→4967B0`，接收者为scene+190h | 检查控制器的记录开关，不能把此调用一概解释为奖励结算 |
| `496410/4967B0` | 仅byte[controller+117C3C]等于1时打开ReplayData.rep | 文件打开是可选且晚于首次结果读取，不能替代更早的同步入口 |
| `453CCE→453CD8→453CDD` | 再执行两次原等待，然后原代码产生返回1 | 必须取得三次真实握手；一次等待或直接到RET均不足 |

这些是本轮重新核对的静态结论，未冒充新原游戏执行。
REA还暴露了工具边界：`callers(4539B0)`为空，但固定原字节 `451AB7` 明确CALL它；
`xrefs(453CB5)`为空也不能否定原RET边。伪代码仍会折叠旧API指针、丢失thiscall，
甚至把API返回值表现为栈检查函数返回值；因此以原字节和ABI为准，保留断言分支的分析警告。

## 修正造成绕路的合同解释

既有 `terminal_unit_frontends_trace.py` 的57项来自 `machine.cpu()`，独立重放器将其
恢复到另一Unicorn并逐边界核对。完整原CPU/内存/权限/ABI/累计指令及写摘要、当前平台
回执和资源清理都保留。总规格并没有要求每种实施方式先捕获宿主机的所有特权寄存器。

后来选择“将实际WOW64上下文导入另一执行环境”时，才需要无损raw64、高位寄存器、
隐藏段缓存、异常递送等额外来源。若继续声称原机现场导入，这些要求一项也不能省；
但不能把该路线的附加要求误用为原执行器与真实OS叶接通的共同前置条件。
此前将二者混用，导致在完整硬件采集和观察器上投入过多。本次纠正路线，不修改原验收标准。

| 方案 | 判定 | 后续动作 |
| --- | --- | --- |
| 现有child-only DR/VEH提供完整原机现场 | **no-go** | 固定716B不足；即使补XSTATE仍缺可信特权/隐藏状态与观察透明性，停止扩建 |
| 在原游戏部署VEH | **尚未资格化** | 有私有分配桥不等于已有合格安装器；父策略、异常链、撤销/静默和干扰都未证明，本轮不部署 |
| 原指令执行器＋同一当前原生所有者 | **conditional-go** | 回到原有合同，先解决真实worker的执行与每线程平台叶路由，未通过前不跑战斗前缀 |

详细可行性证据、官方接口依据与源码摘要见
`analysis/terminal-rea-feasibility-review-v1-20261113.json`。
[Windows XSTATE接口](https://learn.microsoft.com/en-us/windows/win32/debug/working-with-xstate-context)
可以补扩展用户态上下文，但不能据此声称取得完整原机特权状态。

## 替代路线的第一个具体关口

原执行器的真实缺口仍是：旧TASK头和MAIN调度区域为空，`4223A8`会把0x100当作锁；
现有原注册实验止于 `56E0BE CreateThread`，CRT/PTD与事件属于两个helper。
将两个PID合并还不够：必须使锁、TLS和等待叶在对应的真实worker线程上执行。

下一工作单元只实现一个新鲜所有者的最小链：原构造/注册生成真实CreateThread请求，
恢复后原 `56E110` 安装当前TLS，原 `421F50` 从虚表进入原回调，并由原管理器完成首次
让出与唤醒。解释器入口桥只分派原指令，不能把worker替换成“等待后返回成功”的桩。
CreateThread原入口、PTD及指针投影必须有可审计映射；没有映射则在ResumeThread前停止。
TLS在原wrapper安装后验证，不预先伪造。真实PID/TID、锁归属、事件代次、原全部指令和
57项执行器状态须同时可核，成功/失败路径都记录。

之后才从原 `451170/451080` 重新建立派生场景和真实祖先，重建当前资源寿命，连续进入
原等待与453CB5。旧root缺少的祖先不能补写，旧原生句柄不能复活，不能在消费者处另起根。
两例全新原生寿命、独立完整重放、累计摘要、资源/PTD清理和篡改拒绝保持不变。

## 止损预算与桌面约束

- 本轮评估总预算30分钟：环境最多10分钟，分析与路线判定最多20分钟；不发起原游戏采集。
- 下一单元离线实现和审查最多60分钟。若无法给出真实worker执行及每线程叶路由，停止该候选，
  保留首个缺口，不以合并helper或增加测试数报告通过。
- 只有静态所有权关口通过后才执行一次无UI原生预检，外层最多30秒、持久证据最多16MiB。
  不改变原INFINITE等待参数；超时/强制清理一律失败，不延长预算或重复相同配方。
- 失败先按“入口映射、线程/TLS、同步协议、独立轨迹”定位；若设计不能满足原合同，停止并重新选路。
  不自动回退到旧relay、轮询、截图、完整原机搬运或TCG/VM环境扩建。
- 当前不占用桌面。将来确需运行原游戏时先告知、取得新的有界窗口；全自动操作，收尾核对
  分辨率、任务栏、工作区及前台恢复，不要求用户手动推进。

## 2026-11-13 接续实测：所有者组件通过，首协作让出尚未通过

约31分钟离线准备后，只跑了一次1.391秒无UI原生预检。原基类worker在同一新鲜PID
的真实线程上执行平台叶，原56E110安装TLS，421F50调用由422290发布的422330，
完成事件返回MAIN，原PTD释放/TLS清零及实际worker/helper exit0均有回执。
原指令、完整guest状态及原生所有权边界明确分开，未扩建原机上下文搬运。

该结果闭合了原先两个helper、无真实worker的缺口，但**没有达到上文的首次协作让出关口**。
451670在首让出前需要GAME时钟、文字队列和派生场景；本轮不伪造这些依赖，不把空的
基类回调升格为场景成功。首关、三次握手、结果消费及正式2/8均保持原标准。
下一步仅离线接续这些原构造，详见[实测范围与剩余依赖](terminal_native_owner.md)。
